Current goal
- JobBot is a Windows desktop app for finding jobs, queueing them for review, generating tailored application documents, and optionally sending them.
- The recent focus has been document generation quality: moving from generic PDF output to a DOCX-first, template-preserving tailored resume flow using [Robert Thom Resume 2026.docx](C:\Projects\JobBot\Robert Thom Resume 2026.docx) as the canonical source.

Current runtime stack

- Main UI is Tkinter in [dashboard.py](C:\Projects\JobBot\dashboard.py).
- Core pipeline is in [pipeline.py](C:\Projects\JobBot\pipeline.py).
- Resume parsing is in [resume_parser.py](C:\Projects\JobBot\resume_parser.py).
- Document generation is in [doc_generator.py](C:\Projects\JobBot\doc_generator.py).

What changed most recently
- Resume generation is now DOCX-first when the resume source is `.docx`.
- The generator clones paragraph structure from the source DOCX instead of rebuilding from scratch.
- Work bullets preserve real Word numbering/list behavior, paragraph ordering, and source section structure.
- Generated bullet glyph size is explicitly overridden in Word numbering so the black dots are smaller than before.
- Resume generation now auto-fits to 2 pages instead of failing on the first overlength draft.
- Cover letters were rewritten from a resume-dump style into a short structured tailored-letter format.
- Review Queue now shows generation progress stages and disables duplicate Generate clicks while work is in flight.
- There is now a hybrid document-tailoring router: local deterministic tailoring first, then OpenAI escalation for cases that look too broken or too complex.

Current document-generation architecture
1. Resume source is loaded in [pipeline.py](C:\Projects\JobBot\pipeline.py) through `_load_resume()`.
2. DOCX resume parsing expects richer cached structure, not just flattened text.
3. [doc_generator.py](C:\Projects\JobBot\doc_generator.py) can build a local `DocumentTailoringPayload`:
   - tailored work entries
   - tailored key skills
   - cover letter text
4. [pipeline.py](C:\Projects\JobBot\pipeline.py) calls `_prepare_document_tailoring(...)`:
   - build local payload
   - quality-check it
   - if needed, escalate to OpenAI through [match_scorer.py](C:\Projects\JobBot\match_scorer.py)
   - validate AI output
   - retry AI once if the first AI payload fails quality checks
   - otherwise fall back to local payload
5. [doc_generator.py](C:\Projects\JobBot\doc_generator.py) renders:
   - `resume.docx`
   - `resume.pdf` if export succeeds
   - `cover_letter.txt`
6. DOCX resumes are exported to PDF and checked for page count. If they exceed 2 pages, the generator retries with tighter fit passes.

Current DOCX/PDF behavior
- DOCX is the preferred canonical resume source.
- PDF export order in [doc_generator.py](C:\Projects\JobBot\doc_generator.py):
  - Microsoft Word COM
  - LibreOffice from `PATH`
  - LibreOffice from common install paths such as `C:\Program Files\LibreOffice\program\soffice.exe`
- If PDF export still fails, generation can complete as `generated_docx_only`.
- Auto-fit tries to shorten bullet wording first, then trim lower-priority bullets, then shorten key skills if needed.

Current OpenAI document-tailoring behavior
- OpenAI is no longer just a configured key; it is wired into document generation for complex cases.
- The structured AI payload type is [document_tailoring.py](C:\Projects\JobBot\document_tailoring.py):
  - `work_entries`
  - `key_skills`
  - `cover_letter_text`
  - `route`
  - `provider`
  - `model`
  - `fallback_reason`
  - `retry_count`
- The router logs these decisions in [pipeline.py](C:\Projects\JobBot\pipeline.py):
  - `Escalating document tailoring to AI...`
  - `AI tailoring accepted ...`
  - `Falling back to local tailoring ...`
- Important current UX gap:
  - whether a given document run used `local`, `openai`, or `fallback` is visible in the global log but not clearly surfaced in the Review Queue details yet.

Known current issues and rough edges
- AI route visibility is still weak. The app logs escalation and fallback decisions, but the user cannot easily tell from the Review Queue whether OpenAI was actually used.
- Full `unittest` runs have been unreliable lately because document-export tests can hang on live `WINWORD` or `soffice` processes in this environment.
- There is a leftover `tmp_smoke` directory from smoke-testing that could not be fully removed because some files were locked.
- The worktree is noisy:
  - many `__pycache__` files
  - many `tests/_tmp/...` directories
  - large `.venv312` site-packages changes showing as untracked
- The generated resume wording is better than before, but some roles can still produce locally tailored bullets that read stiffly enough to trigger OpenAI fallback attempts.

Current user expectations that matter
- User wants the resume to visually match the original DOCX template as closely as possible.
- User is okay with assertive inferred tailoring and plans to do the final truth review themselves.
- User wants generated resumes to end at 2 pages maximum, with auto-fitting instead of immediate failure.
- User wants clearer visibility into whether OpenAI was actually used during document generation.
